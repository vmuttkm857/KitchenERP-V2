# KitchenERP V2 回歸驗收需求

> 本 checklist 只描述可觀察的功能與業務行為，不規定 Streamlit、舊 SQL 或舊 session state 實作。V2 完成前應逐項驗收；標示「待確認」的項目需先由產品決定。

## A. 主檔

- [ ] 可以建立、搜尋、修改、停用及恢復食材分類。
- [ ] 可以建立、批次維護、停用及恢復菜色分類。
- [ ] 可以建立供應商（代碼唯一、名稱必填），並搜尋、修改、停用/恢復。
- [ ] 供應商停用不會消失既有食材、快照、採購或備料歷史。
- [ ] 可以新增食材：代碼、名稱、分類、基本單位、目前單價、主供應商、備註。
- [ ] 食材代碼重複或其他驗證失敗時，不留下半筆食材/價格資料，且使用者草稿仍可修正後再送出。
- [ ] 食材新增成功時，同時存在初始價格歷史；兩者任一步失敗都 rollback。
- [ ] 修改食材目前單價時，同時追加價格歷史；舊歷史不被覆蓋。
- [ ] 食材列表支援名稱/代碼搜尋、分類/狀態篩選、SQL 分頁與直接頁碼輸入。

## B. 菜色與標準配方

- [ ] 可以建立菜色，且菜色代碼與名稱分別唯一。
- [ ] 菜色可指定菜色分類、修改名稱/分類/啟用狀態與備註。
- [ ] 菜色列表有搜尋、分類、狀態、排序、COUNT/LIMIT/OFFSET；不一次載入所有菜色。
- [ ] 每列仍可直接進入編輯與標準配方，且操作對真正 `dish_id`。
- [ ] 配方可以按供應商與食材關鍵字搜尋，候選採 SQL 分頁，不預載全部食材。
- [ ] 配方可一次選多個食材，單一 transaction 加入；任一筆失敗則全批 rollback。
- [ ] 同一 `dish_id + ingredient_id` 不可重複；已在配方的食材在選取 UI 不可再加入。
- [ ] 新加入食材可先以安全預設量存在，並於目前配方區批次填寫量、單位、耗損、備註。**quantity=0 的正式儲存政策待確認。**
- [ ] 配方的使用單位可不同於食材基本單位，例如雞丁基本單位「斤」、配方「g」。
- [ ] 修改配方量、單位、耗損與備註只有正式儲存才寫 DB；儲存使用真正 `dish_ingredient_id + dish_id`。
- [ ] 可選多筆刪除配方食材，含二次確認、transaction 與 rollback。
- [ ] 配方操作後保持在同一菜色的配方工作區，直到使用者主動關閉。
- [ ] 單份成本採含耗損配方量換到食材基本單位後乘目前單價；不能安全換算時顯示待確認而非錯誤成本。

## C. 單位與數量

- [ ] 新資料統一使用 `ml`；舊 `mL` 可讀取且被視為 `ml`。
- [ ] `g ↔ kg ↔ 斤` 正確換算，且 `1 斤 = 600 g`。
- [ ] `ml ↔ L` 正確換算。
- [ ] 片、個、隻、包、盒等不同維度單位不被自動猜測換算。
- [ ] 所有需求、成本與採購計算保持 Decimal 級精度；展示可格式化但不得改底層量。

## D. 菜單與週排餐

- [ ] 可以建立有名稱、日期區間、分類與備註的菜單。
- [ ] 結束日期早於開始日期時拒絕建立/儲存。
- [ ] 菜單列表可搜尋、按分類/狀態篩選、以 SQL 分頁、直接輸入頁碼跳頁。
- [ ] 可從主列表選定唯一「正在編輯」的 menu；即使搜尋/換頁，不能因 row index 對錯 menu。
- [ ] 每張菜單可管理動態餐別：新增、排序、停用、重新啟用；不寫死早餐/午餐/晚餐。
- [ ] 同菜單相同餐別名稱不可重複。
- [ ] 新菜單第一次開啟工作區時建立預設餐別；既有餐別不會每次畫面刷新重複建立。
- [ ] 週矩陣顯示開始日至結束日（包含兩端）的每個日期與啟用餐別。
- [ ] 空餐格可直接加菜；管理空餐格可以 disabled 或顯示無菜色，但不能阻礙加菜。
- [ ] 加菜與管理均使用真正 `menu_day_id`、`menu_meal_type_id`、`menu_dish_id`。
- [ ] 每餐格待加入籃跨搜尋、分類、分頁保留，但不同餐格互不混用。
- [ ] 加菜批次 transaction、重複菜色檢查及個別 diner count 正確。
- [ ] 管理餐格可修改 diner count、備註、順序數字、上移/下移及批次刪除。
- [ ] 上/下移只交換必要相鄰兩筆；第一筆上移/最後一筆下移不可用。
- [ ] 任一排序、直接改順序、批刪後，sort order 必為連續 `1..N`。
- [ ] 批次刪除只 rerun 一次，並在同一 transaction 完成刪除與排序重整。
- [ ] 一日複製以餐別名稱對應，加入模式不重複，覆蓋需二次確認。
- [ ] 整週複製先驗證目的菜單具備來源使用的餐別；整週一個 transaction，任一天失敗都 rollback。
- [ ] 週菜單可輸出可編輯版與列印版 Excel，日期與餐別格對應正確。

## E. 廚房作業／備料

- [ ] 可選菜單與單餐、單日、整張菜單三種範圍。
- [ ] 可依菜色、食材、供應商檢視同一份備料資料。
- [ ] 備料量 = 配方每人用量 × 該餐格用餐人數 ×（1 + 耗損率）。
- [ ] 備料不使用 package size、最小訂購量、正式採購量或實際配送量。
- [ ] 未配方菜色、找不到食材、不可換算單位均顯示警示，不能悄悄省略或猜算。
- [ ] 自動易讀顯示：1000 g→1 kg、1250 g→1.25 kg、2500 ml→2.5 L；原始模式不改單位。
- [ ] 數量顯示整數無小數；非整數最多兩位並去尾零，例如 83.333333→83.33。
- [ ] ERP 與 Excel 使用相同數量 formatter。
- [ ] 可直接下載目前範圍的 A4 列印 Excel；不要求「產生」再「下載」兩步。
- [ ] 整張菜單範圍才顯示整週配料總覽匯出。
- [ ] 列印 Excel 每頁有完整頁首與單一欄表頭；正常單一道菜區塊不跨頁，只有超大區塊可續頁。
- [ ] Excel 文字不會被當作公式執行。

## F. 食材需求

- [ ] 候選菜單可按期間、名稱、複數分類篩選；NULL category 視為未分類。
- [ ] 已選 menu IDs 不會因搜尋/分類改變而消失，即使不在目前 100 筆候選中。
- [ ] 可手動同選不同分類的菜單。
- [ ] 可按多個需求日期快速加入所有有效菜單；日期判定為 start ≤ date ≤ end，且不受搜尋/分類限制。
- [ ] 系統需求以食材與最終可安全確定的單位彙總。
- [ ] 需求明細保留 menu/date，不跨 menu 合併 date schedule。
- [ ] 可換算時的建議採購量初值等於系統需求量；此階段不做包裝、最小訂購量或進位。
- [ ] 不可換算單位標記待確認，且不給假成本或假採購量。
- [ ] 可在彙總/詳細呈現之間切換而不改變計算。

## G. 需求快照與需求確認

- [ ] 確認需求後建立 immutable-like hard copy：來源菜單/日期、items、成本/價格/單位/採購規格與逐日 schedules。
- [ ] 建快照失敗時，snapshot、items、schedules 均不留下半筆資料。
- [ ] 同一個 UI session 相同計算結果不能重複建立 snapshot；跨 session 的重複策略 **待確認**。
- [ ] 需求確認可按待建立叫貨單、已建立叫貨單、全部查詢；狀態由是否存在 `purchase_order.source_snapshot_id` 判定，不新增 snapshot status 欄位。
- [ ] 從食材需求導向的 pending snapshot 即使不符合當前篩選仍可自動被選中。
- [ ] 可以調整 snapshot 的採購量與採購單位，不會回寫原始需求、菜單、配方、食材或價格。
- [ ] 重量採購單位可安全轉換；其他單位只能保留原單位。
- [ ] 未建立正式採購單的 snapshot 可二次確認後刪除；已建單 snapshot 禁止刪除，且歷史仍可查。

## H. 正式採購與配送

- [ ] 可以由 snapshot 建立正式採購單，並將 item/schedule 資料複製為正式 order/items/allocations。
- [ ] 建單 transaction 任何一步失敗都 rollback。
- [ ] 建立 order 不會刪除或修改來源 snapshot。
- [ ] 採購管理可按進行中、已結案、全部以及名稱/期間查詢；候選限制不一次載入完整歷史。
- [ ] 每日叫貨具有明細、叫貨表、帳務明細與分帳呈現，並支援供應商/日期篩選與 Excel。
- [ ] delivery date 可與 requirement date 不同；只修改 allocation 的 delivery date，不改需求硬拷貝日期。
- [ ] 無既有 delivery allocation 時，畫面預設 delivery date= requirement date，但未儲存前不得 INSERT。
- [ ] 配送可拆分、額外配送、改量/日期/刪除；換算後配送合計不得超過正式 ordered quantity。
- [ ] 結案只改 order 狀態與結案時間，保留 items/allocations；已結案不能改配送，恢復後可繼續操作。
- [ ] 刪除正式採購單會連動刪除 order items/allocations，但不刪來源 snapshot。

## I. 技術/資料完整性驗收（可觀察結果）

- [ ] 所有列表搜尋/篩選/分頁在資料量大時仍只取目前頁資料。
- [ ] 所有批次新增、批次更新、批次刪除均具原子性和可讀錯誤訊息。
- [ ] 所有使用者可見資料操作以真正資料 ID 身份辨識，從不依 row index、排序位置或顯示名稱更新。
- [ ] DB constraint 失敗不洩露秘密/連線資料，且 user message 可區分重複、FK、CHECK、NOT NULL 的主要情況。
- [ ] PostgreSQL date、timestamp、boolean、numeric/Decimal、JSONB 在畫面與 Excel 邊界均正確呈現。
- [ ] 每個頁面具有可測量的 query budget；正常 UI 操作不出現 N+1 或不必要的全量預載。
